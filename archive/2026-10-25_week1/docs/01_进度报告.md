## 二、遇到的问题与解决（摘要）

| 问题 | 根因 | 解决 |
|---|---|---|
| SDK 装不上 macOS | 官方只发 Linux/Windows wheel，含闭源视频解码器 | 拆 manylinux wheel 装纯 Python 部分 + 3 个补丁（导入容错、解码器按需创建、连接类型 `is`→`==`） |
| 视频流不可用 | 同上（解码器闭源） | 实测 TCP 40921 为裸 H.264，PyAV 解码成功；已集成进自检脚本 |
| F1 与论文差 2 倍 | NYU `.mat` 图像/深度为**转置存储**（等价旋转+镜像），模型一直在看侧翻图 | 还原方向后 AbsRel 从 0.10+ 降到 0.0624 |
| 检测全部漏检 | hf-mirror 下载的 Grounding DINO 权重哈希不符（大小对、内容错） | 改用 HF 缓存中校验过的权重 |
| 数据下载受限 | GitHub/COCO/NYU 直连超时、代理不稳 | 多源并行（hf-mirror / ModelScope）+ 多线程分块续传工具 |

## 五、小结：哪一步最难、差多少、为什么

**最难的一步是让整条「真机 → 数据 → 模型 → 指标」链路在 macOS 上跑通**，而不是模型本身。
官方 SDK 对 macOS 没有支持（无 wheel、无视频解码器），数据源在国内网络下也不稳定。
最后是靠读 SDK 源码定位到「视频流其实是 TCP 40921 的标准 H.264」才解决，这也说明
遇到平台限制时先查协议、再找替代实现，比等官方支持更有效。

**与论文的差距**：F1 差 0.009 AbsRel / 0.019 δ1（约 1.5–2%），主要来自远处动态范围压缩和
浴室镜面反射场景（已逐例分析）；F2 差 5 个 AP（约 10%），主要是实现差异（HF 版 vs 官方 CUDA 算子）、
只测前 500 张且未调阈值；F3 差 28–31 个百分点，但**方法与论文一致**，差距来自用本地 3B 小模型
替代了论文的 text-davinci-003，后续用免费大模型/7B 模型可缩小。
