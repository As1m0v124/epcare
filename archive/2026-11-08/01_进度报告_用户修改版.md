## 二、验收项 1：稳定复现「指令堆积卡死」，并给出已消除卡死的版本

### 2.1 现象与根因

- 现象：网页上连续操作底盘/机械臂一段时间后，后续指令长时间不执行，最后只能重启控制服务；  
  期间状态接口还正常，很容易误判成机器人坏。
- 根因：`/move`、`/arm`、`/grab` 在 FastAPI 线程池里**各自并发**调 SDK；EP 的 SDK 动作通道一次只能执行一个动作，  
  请求就在服务里无限排队。排队越长，后面的指令等得越久；状态接口读缓存，所以页面“看着正常”。  
  上周只给 `/arm` 加了 try-lock（忙则 429），没有覆盖 `/move` 与跨接口的堆积，所以问题仍在。

### 2.2 修复方案（已实机运行）

- 所有动作统一走**有界队列 + 单工作线程**：队列容量 2（1 条执行 + 1 条排队），第 3 条起立即返回 **429**；
- 单条动作执行超过 12 秒返回 **504**，不再无限等待；
- **急停会清空队列**，排队中的动作全部取消；
- 队列模式下强制等待动作完成再执行下一条，避免连续提交撞 SDK 的 `already performing`；
- 控制服务 `/state` 增加 `queue: {size, max, legacy}`，可直接看到当前排队数；
- 保留 **`EPCARE_LEGACY=1`** 开关切回旧行为，用于复现对比；默认关闭。

### 2.3 真机对比（同一脚本、同一台 EP，电量 45–95%）

脚本：`scripts/repro_pileup.py --n 36`（36 条并发、每条 10mm 步进、正负交替，第 37 条为探测指令）。

| 版本                    | 36 条批量结果                      | 请求延迟 p50 / max            | 堆积期间 `/state` | 堆积期间新指令          | 判定     |
| --------------------- | ----------------------------- | ------------------------- | ------------- | ---------------- | ------ |
| 旧版（`EPCARE_LEGACY=1`） | 两次：22×200+14 超时 / 33×200+3 超时 | **18.3/20.0s；12.5/20.0s** | 0.001s        | **10.0s 超时**     | ❌ 卡死复现 |
| 修复版（默认）               | 3×200 + **33×429**            | **0.01s / 1.22s**         | 0.003s        | **0.40s 返回 200** | ✅ 不再卡死 |

> 旧版的 p50 会随机器人状态/队列残余动作浮动（12.5–18.3s）；**稳定判据是「堆积期间第 37 条探测指令 10 秒超时」**，而不是固定 p50。

![旧版卡死时的完整网页](evidence/web_freeze_annotated.png)

- 证据：`results/pileup_before.json`、`results/pileup_after.json`；审计日志 `logs/control_audit.jsonl` 含 `queue_full` 记录；

- 解释：修复版里 429 是**主动限流**，不是故障；它把“越堆越慢”变成“立即告诉调用方忙”，因此状态和新指令始终能及时响应。

### 2.4 舵机连续控制

**为什么不能连续控制：EP 机械臂只开放“位置步进”接口，没有可用的“速度”接口，所以做不到底盘那种匀速连续控制。**

1. 底盘有 `drive_speed`（速度指令）；机械臂高层 `robotic_arm.move(x,y)` 只有位置增量，没有速度/时间参数；
2. `servo.drive_speed` 低层速度模式与机械臂高层位置控制互斥：实测失败，进入后会锁死机械臂、只能重启，已禁用；
3. SDK 动作通道一次只执行一个动作：高频发小步会报 `already performing`；单步 <8–10mm 会被静默忽略（动作仍返回成功）；
4. 因此只能“发 10mm → 等完成 → 回读位置 → 再发下一步”，属于**分段位置控制**，不是匀速线性控制。

结论：能做到“连续步进”，但做不到“线性速度”；这是接口和机械结构限制，不是参数没调好。

在这个限制下，真机连续 20 步 ±10mm，每步完成后回读位置（工作区中部，避免行程边缘干扰）：

| 指标      | 结果                                  |
| ------- | ----------------------------------- |
| 执行成功    | **20/20**（HTTP 200）                 |
| 单步到位误差  | 平均 **1.55mm**，最大 **2mm**，20/20 ≤3mm |
| 方向正确    | 20/20                               |
| 20 步净漂移 | x +3mm（正负交替，理论 0）                   |

证据：`results/servo_stability.json`。之前“按多了丢步/卡住”主要来自并发排队（见上），队列化后连续步进全部执行；  
机械臂位置控制仍是“发 10mm 步进 + 等完成”的开环步进，单步误差 ≤2mm，更细的步长（<8mm）仍会被 SDK 忽略，这是已知边界。
