### 🔧 解决的问题（3 个，含根因）

| 问题 | 根因 | 解法 |
|---|---|---|
| `uv pip install robomaster` 报「无匹配平台的 wheel」 | DJI 官方只发布 Linux/Windows wheel；包内唯一编译模块是 Linux x86_64 视频解码器 libmedia_codec（闭源） | 拆开 manylinux wheel，把纯 Python 部分装进 ep38，对 `media.py` 两处 import 打容错补丁；依赖 4 个纯 Python 包单独装（netifaces 源码编译约 10 分钟） |
| SDK `initialize()` 直接崩溃，控制全不可用 | 初始化相机模块时**急切创建**视频解码器，而 macOS 上 libmedia_codec 不存在 | 解码器改为按需创建；`start_video_stream/start_audio_stream` 在无解码器时明确报错返回，不再拖垮连接 |
| 命令行传参连不上机器人（内联脚本却能连） | SDK 用 `is`（对象身份）比较连接类型；从命令行传入的 `'sta'` 与内部常量不是同一字符串对象，三个分支全部落空 | `conn.py` 三处 `is` 改为 `==`（SDK bug，上游可报告） |

另发现：EP 电量为**订阅推送式**接口（非一问一答），需 `sub_battery_info(freq=1, callback=...)` 订阅后延时读取。

### 🎥 10-25 17:5x 视频流突破：直连 TCP 40921 拿裸 H.264

- 读 SDK 源码发现：视频流只是普通 TCP 流（端口 40921），SDK 先发 `_stream_sdk(1)`/`_video_stream(1)`

- 用 PyAV 直接解码成功，`ep_selfcheck.py` 已集成：**保存 10 张 640×360 实拍图**（results/selfcheck_photos/）；
- 结论：**macOS 原生支持 EP 实时画面与拍照**，驾驶舱实时视频不需要台式机或 Docker。
  本项从「阻塞」转为「已完成」，REPRO.md 已更新方案说明。

### 🛑 10-31：遥控"松手不停"问题（已修复）

- 根因：停止时驱动线程与 stop() 竞态——停指令之后线程又补发了一次旧速度，之后无人再发指令，机器人以最后速度持续运动；
- 修复：停止时先等驱动线程退出再发 `drive_speed(0)` + `stop()`；新增 **1.5 秒无心跳自动停**（防网页失联）；
  前端按住时每 0.4 秒发心跳，松手/失焦/切标签立即停止；
- 附带：反复开关流会导致机器人视频模块异常（推流数据损坏），需机器人重启恢复；代码已改为首次连接不重复开流。

- 键盘绑定补充：`PgUp/PgDn` 机械臂前后、`小键盘 8/2` 上下（按住连续动）、`Enter` 爪子闭合、`Backspace` 张开；
  已用页面模拟按键实测（审计记录到 arm -8mm）。

### ⚠️ 10-31：舵机速度模式实验（失败并记录）

- 目的：让机械臂按住时做线性连续动作；尝试 `servo.drive_speed(index,speed)`。
- 结果：机械臂不动，且该 API 会把舵机切入「舵机模式」，`pause` 无法切回，
  机械臂 IK 控制被锁死——需要机器人重启复位。
- 结论：**不要用 servo 速度接口控制机械臂**；连续动作改用「阻塞小块首尾相接」
  （每次 6mm/等完成即发下一次），重启后验证。
- 错题本 #5（Seen 1×）：舵机底层接口与机械臂高层接口互斥，实验性指令先在单舵机上小步验证，
  并准备复位路径（重启）。

### 🧪 10-31 机械臂连续动作调参（阶段性结论）

- `arm.move` 最小有效步长约 **8–10mm**（6mm 被静默忽略、动作仍报成功）；
- 连发过快（<0.25s 间隔）会被丢弃，5 次只执行约 3 次；
- 现方案：**闭环步进**（每步 10mm，发完轮询位置确认移动 ≥5mm 再发下一步），参数已在前端；
- **电量 ≤ 40% 时机械臂接受指令但不动作**（舵机 valid、速度 0、无报警；37% 时复现）；
  结论：需充电到 80% 以上再验证连续手感——低电量时机械臂疑似功率保护；
- 经验：舵机底层 `servo.drive_speed` 会切模式锁臂（重启可解），不要再用于机械臂。

**错题本 #6（Seen 1×）**：低电量会让机械臂"假死"（指令成功、位置不动），排查硬件前先看电量。

### 🔋 10-31 换满电电池后验证

- 换电池（100%）→ 机械臂恢复动作，证实「≤40% 电量假死」是低电量功率保护；
- 闭环步进实测：5 步 × -10mm，总耗时 2.78s（约 12mm/s），位置 108→74，无丢步；
- 前端按住键位即按此节奏连续执行；步长可按需调整（10mm/步，上下 6mm/步）。

### 🔁 10-31 满电复测舵机速度接口（排除低电因素）

- 满电 100% 下 `servo.drive_speed(1/2, 6)` 返回 **False**（命令被拒），舵机不动；
- 随后 `arm.move(-10)` 仍正常（134→127），未再锁臂；
- 结论：舵机速度模式在 EP 机械臂上不可用（与电量无关），**线性动作仍采用闭环步进**；
- 连发实测（满电）：5×-10mm 阻塞连发 Δ=-27mm（部分丢弃），非阻塞 10×-4mm 仅 Δ=-4mm
  → 闭环确认步进是唯一稳妥方案。

### ⌨️ 10-31：键盘"没反应"根因=输入框焦点

- 焦点停在检测输入框时，键盘控制被有意忽略（避免打字误触发）；用户以为按键失效。
- 修复：点击画面/遥控区/机械臂区自动失焦；检测与找东西提交后自动失焦；页面加提示「先在画面上点一下再按键」。
- 实测：输入框聚焦→点画面（焦点回 BODY）→按 W 触发 drive_hold(0.3m/s)，松手 stop_drive。

### 🧨 10-31：SDK 动作通道卡死（已定位）

- 现象：按键/命令都能到达后端，但底盘、机械臂都不动；`/move` 20 秒超时，而 `/state` 正常（走缓存）。
- 根因：控制服务里长时间实验后，SDK 动作通道卡死（动作永远等不到完成）。
- 处理：重启控制服务 + 重连即恢复（前进/后退 0.2m 正常，2 秒完成）。
- 加固：move/arm 超时后自动标记连接失效（需重新连接），避免半死连接继续吞指令。

**错题本 #7（Seen 1×）**：状态接口正常不等于控制链路正常；动作超时应自动判定连接失效并要求重连。

### 🔌 10-31：机器人整体掉线（网络/系统级）

- 现象：小车卡死、画面不刷新、ping 与 SDK 广播均不可达——机器人自身 Wi-Fi/系统挂起；
- 处理：机器人关机重启；控制服务新增「动作超时 → 标记失效 → 后台自动重连（12 次×5s）」；
- 经验：频繁断开/重连会加重机器人网络模块负担，日常保持单连接+心跳即可。

### 🌐 10-31：跨网段连接问题（重要）

- 现象：Mac 换了网络（10.67.201.x），机器人在 10.197.63.x，SDK 自动扫描失败、页面全无响应；
- 排查：ping 不通但 **SDK UDP 广播仍能发现机器人**，TCP 40923 实际可达 —— 问题是 SDK 自动扫描选错网卡；
- 解决：控制服务支持 `EP_IP` 环境变量（设置 `config.ROBOT_IP_STR` 跳过扫描）：
  `EP_IP=10.197.63.238 ep38/bin/python -m uvicorn services.control.server:app ...`；
- 验证：连接成功、画面 65KB、前进 0.1m 1.16s、电量 88%。

**错题本 #8（Seen 1×）**：网络层"找不到机器人"先分三层排查：ping（IP 可达）→ UDP 广播（同广播域可见）→ SDK 扫描/网卡选择；广播能发现就别信自动扫描。

### 📐 10-31：机械臂限位实测 + SDK 有符号解码修复（重要）

- **SDK bug**：`robotic_arm` 位置用无符号整数解码（`<II`），y 的负值变成 4294967xxx，
  导致「某方向不动/位置异常」。改为有符号（`<ii`），补丁已同步进安装脚本；
- 实测限位（随姿态耦合，非固定矩形）：
  - y（升降）：**-69 ~ 117**；x（前后）：**69 ~ 194**（在 y≈130 时 x 上限约 194；y≈60 时 x 可达 209）
- 前端：机械臂步进 1 秒内无位移 → 判定到限位，提示并自动停止该方向，不再空转；
- 结论：无需 App 校准，坐标异常是解码 bug；限位可用不必硬性矩形截断。

### 🎚 10-31：机械臂上下"到限位"误报修正

- 实测上下方向正常：y 105→136→77（同一姿态下范围比首次扫描更大，证实限位随姿态耦合）；
- 误报原因：前端 1 秒无位移即判限位，而部分姿态单步需要 >1 秒；
- 修正：判定窗口 1s→3s、容差 5mm→3mm、连续两次失败才提示「已到限位」。
